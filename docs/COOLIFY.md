# Развёртывание в Coolify

Репозиторий: https://github.com/dark321985/yanov, ветка `main`. Этот документ описывает подготовку; реальное развёртывание на сервере выполняется отдельно. PostgreSQL внешняя: контейнер базы в production не создаётся. Доступы хранятся только в приватном окружении.

## Быстрый первый запуск с пустой внешней PostgreSQL

1. Подготовить отдельную **пустую PostgreSQL 17** у своего провайдера. Административному пользователю нужны права создать таблицы, установить `btree_gist` и создать/настроить ограниченную роль приложения. Если провайдер не разрешает создание ролей, роль создаётся заранее через его панель.
2. Открыть локальный **`.env.production`**: это игнорируемый Git-файл для приватного заполнения. Безопасный образец в репозитории — **`.env.production.example`**. Локальный `.env` с тестовыми данными/подключением не менять и не переносить в production.
3. Приватно заполнить `APP_URL`, `DATABASE_URL`, `MIGRATION_DATABASE_URL`, `MIGRATION_EXPECTED_DATABASE`, `MIGRATION_EXPECTED_ROLE`. Обе строки БД указывают на один внешний сервер и одну базу, но на разные логины. Runtime-логин должен быть ограниченным; если его ещё нет, первый запуск создаст его с паролем из приватного `DATABASE_URL`. Спецсимволы в URL-компонентах кодируются. Политика TLS задаётся через `DATABASE_TLS`, а не `sslmode` в URL.
4. В Coolify добавить приложение из этого Git-репозитория: Dockerfile, Base Directory `/`, Dockerfile Location `/Dockerfile`, порт `3001`, свой HTTPS-домен.
5. Импортировать заполненные переменные в Coolify. Для секретов выбрать **Runtime only / Not available during build**. Сам `.env.production` не загружать в Git и не включать в Docker build context.
6. При первом deployment оставить **`INITIALIZE_EMPTY_DATABASE=true`**. `npm start` до запуска API проверит ожидаемую базу/административную роль, убедится в пустоте базы, создаст схему и ограниченную runtime-роль. Копирования тестовых записей, локальных оплат, пароля владельца или Telegram-настроек нет.
7. Открыть интерактивный терминал контейнера Coolify и выполнить `node dist/server/scripts/owner.js setup`. Пароль вводится скрыто дважды; не передавать его в аргументах команд.
8. После успешного запуска задать **`INITIALIZE_EMPTY_DATABASE=false`**. Если административное соединение не требуется постоянно, удалить `MIGRATION_DATABASE_URL` из runtime после создания владельца и передавать его только maintenance-командам.
9. Проверить вход и пустые списки. Перенос локального демо-набора не выполняется.

Если `INITIALIZE_EMPTY_DATABASE=true` случайно останется включённым, обычный перезапуск лишь проверит уже существующую схему и сохранит записи. Новые/изменённые миграции автоматически на непустую базу не накатываются: требуется контролируемое обновление с backup, описанное ниже. Чужая непустая база без схемы приложения отклоняется без очистки.

## SQL-файл пустой схемы

**`db/schema.sql`** — готовый импорт структуры и начальных настроек. Он сформирован из SQL-миграций, содержит их registry/checksum и не содержит клиентов, складов, договоров, оплат, сессий и пароля владельца. Это не дамп локальной БД.

Обычный путь — автоматическая инициализация первого запуска выше. Ручной SQL-импорт — альтернативный путь: в защищённой SQL-сессии подтвердить цель через `skladno.expected_database` и `skladno.expected_role` (session settings), затем выполнить весь файл одной транзакцией. Имена цели вводятся приватно в SQL-клиенте; без них либо в непустой базе импорт останавливается. После ручного импорта также нужны runtime grants и настройка владельца.

Повторное создание файла из исходных миграций без доступа к БД: `npm run db:schema`.

## Ресурсы

1. Создать отдельную PostgreSQL 17 с постоянным хранилищем. Установку `btree_gist` должен разрешать пользователь миграций. В образе установлены dump/restore tools этой major-версии; при выборе другой major согласовать соответствующую версию инструментов резервного копирования.
2. Добавить приложение из Git, build pack Dockerfile, файл `/Dockerfile`, context `/`.
3. Порт приложения 3001, домен с HTTPS. Прямой публичный доступ к внутреннему порту приложения/БД закрыт.
4. Healthcheck `/health/ready`. Liveness `/health/live` не проверяет БД.
5. Volume для защищённых бэкапов, например `/backups`, с правом записи у runtime-пользователя контейнера `node`. Архивы дополнительно копируются во внешнее хранилище.

## Переменные

Имена перечислены ниже; значения не публиковать в Git, чатах, screenshots или логе команды.

| Переменная | Назначение |
| --- | --- |
| `NODE_ENV=production` | Production-режим |
| `HOST=0.0.0.0`, `PORT=3001` | Внутреннее прослушивание |
| `APP_URL` | Полный HTTPS URL приложения, определяет origin и ссылки Telegram |
| `APP_TIMEZONE` | Начальное значение Europe/Moscow; рабочий часовой пояс далее в настройках БД |
| `DATABASE_URL` | Соединение ограниченной runtime-роли |
| `MIGRATION_DATABASE_URL` | Отдельное административное соединение, только для release/обслуживания |
| `DATABASE_TLS` | `verify-full` для проверяемого TLS либо явно выбранный `disabled` для внутренней сети |
| `TRUST_PROXY_HOPS=1` | Только за одним доверенным Coolify proxy; прямой доступ закрыт |
| `RUN_SCHEDULER=true` | Фоновая генерация начислений и уведомления |
| `TELEGRAM_BOT_TOKEN` | Серверный секрет бота, необязателен до подключения |
| `MIGRATION_EXPECTED_DATABASE` | Точное ожидаемое имя базы для preflight, не выводится |
| `MIGRATION_EXPECTED_ROLE` | Точная ожидаемая административная роль, не выводится |
| `INITIALIZE_EMPTY_DATABASE` | `true` только для первого создания схемы; затем `false` |
| `PRODUCTION_MIGRATIONS_ALLOWED=true` | Явное разрешение release-команде применить production-миграции |
| `MIGRATION_BACKUP_FILE` | Путь к свежему custom-format dump и соседнему `.sha256` |
| `BACKUP_DIRECTORY=/backups` | Постоянная защищённая папка резервных копий |

Не добавлять `sslmode`/ключи TLS внутрь строки соединения: политика TLS задаётся отдельно. Не использовать префикс `VITE_` для секретов.

Секрет миграций по возможности доступен только release/maintenance-команде. После настройки владельца не требуется runtime-серверу; используйте возможности Coolify для разделения окружений и удаляйте административный секрет из постоянного runtime-окружения, если обслуживание запускается отдельно.

## Последующие release с изменением схемы

Собрать образ Dockerfile. Не запускать миграции одновременно в нескольких репликах и не помещать их в обычный CMD приложения.

В maintenance/release-контейнере того же образа с секретами и ожидаемой идентичностью:

```sh
node dist/server/scripts/backup.js
```

Выбрать созданный файл через защищённую серверную файловую среду и задать `MIGRATION_BACKUP_FILE`. Это custom-format PostgreSQL dump; рядом должна быть checksum. До миграции скрипт сверит цель, целостность и читаемость архива. Перед рискованными изменениями также выполняется пробное восстановление в отдельную БД.

```sh
node dist/server/scripts/migrate.js
node dist/server/scripts/grant-runtime.js
```

`DATABASE_URL` указывает на отдельную runtime-роль с её секретом. `grant-runtime` проверяет ограничения роли и обновляет grants новых таблиц. Секреты не передаются аргументами команд.

При необходимости первого владельца после ручной инициализации настроить в интерактивном терминале:

```sh
node dist/server/scripts/owner.js setup
```

Пароль вводится скрыто дважды, 12–128 символов. Public-регистрации нет. Не передавайте пароль через argv, echo, heredoc или логи. Настройка не перезаписывает существующего владельца.

После этого запустить приложение штатно. Проверить `/health/ready`, вход, пустую базу, создание склада/клиента/аренды, ручную оплату и график. Production не заполняется демоданными.

## Telegram

1. Создать бота и сохранить его token только в Coolify secrets.
2. Запустить диалог с ботом от имени получателя.
3. В защищённых настройках указать chat ID, число дней и время напоминания.
4. Нажать «Отправить тест» и проверить результат.
5. Явно включить автоматические уведомления.

Без token приложение полноценно ведёт аренду и оплаты, но сообщения не отправляет. Настройка токена требует перезапуска контейнера; число дней и получатель меняются в админке.

## Обновления

Для обновления с изменением схемы: свежая резервная копия → проверка читаемости/целостности → миграция одним процессом → обновление grants runtime → новый контейнер → readiness и релевантная проверка изменённой функции. Не восстанавливайте старый дамп поверх новых данных автоматически при ошибке старта.

## Резервные копии

Настроить ежедневную scheduled job Coolify, запускающую `node dist/server/scripts/backup.js` в окружении с доступом к БД и backup-volume. Внешняя копия обязательна: один volume не защищает от потери сервера. Начальная политика хранения — 7 ежедневных и 4 еженедельных копии; удаление старых архивов включается отдельной согласованной процедурой, а не выполняется приложением автоматически.

Восстановление сначала проводить в новой отдельной БД. Сверить checksum, выполнить `pg_restore` через окружение PG-переменных без секретов в argv, проверить количество/связность записей, миграции, владельца и суммы. Только затем переключать приложение по отдельному решению владельца. Восстановление тестового custom-format архива подтверждено локальным `npm run test:backup`.

## Восстановление доступа

При наличии подтверждённого административного доступа к серверу:

```sh
node dist/server/scripts/owner.js reset
```

Пароль вводится скрыто. Все старые сессии отзываются. Публичного обхода пароля нет.

## Границы подтверждения

Dockerfile и конфигурация подготавливаются и проверяются локально. Реальный Coolify deployment, DNS/HTTPS конкретного домена, ежедневное инфраструктурное расписание и настоящая доставка Telegram требуют подключений владельца и проверяются при фактическом развёртывании. Приложение не утверждает, что эти внешние действия уже выполнены.

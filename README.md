# Складно — учёт аренды складов

Веб-платформа для одного владельца: склады, клиенты, индивидуальные условия аренды, ручные оплаты и Telegram-напоминания.

Подробные правила, этапы и критерии готовности: [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).

Для Git/Coolify: [инструкция](docs/COOLIFY.md), [production-шаблон окружения](.env.production.example), [пустая SQL-схема](db/schema.sql). PostgreSQL в production внешняя; локальные демоданные и `.env` не переносятся.

## Текущее состояние

Реализованы серверное хранение, вход владельца, справочники клиентов и складов, аренды с индивидуальной ценой, начисления, ручные частичные и многомесячные оплаты, исправления с историей, календарь, отчёты и настраиваемые Telegram-напоминания. Локальная приёмка завершена: [результаты и ограничения](docs/ACCEPTANCE.md).

Интерфейс на русском языке, для компьютера и телефона. В production нет регистрации клиентов и автоматических демонстрационных записей. Приложение не принимает деньги онлайн: владелец регистрирует фактические поступления вручную.

## Требования

- Node.js 24 LTS и npm 11+.
- PostgreSQL 17 либо Docker для отдельной локальной тестовой БД.
- Docker не нужен для frontend и backend.

## Быстрый локальный запуск

```powershell
npm ci
npm run env:init
npm run db:up
npm run db:migrate
npm run db:runtime
npm run db:check
npm run owner:setup
npm run dev
```

Открыть <http://127.0.0.1:5173>. Vite передаёт `/api` и `/health` локальному backend.

`env:init` создаёт `.env` с локальными параметрами и случайным паролем PostgreSQL. Значения не выводятся. Если файл существует, команда сохраняет его без изменений. Не публикуйте `.env` и не прикладывайте его к диагностике.

`db:up` запускает только отдельный PostgreSQL-контейнер проекта и ждёт его готовности. База слушает только loopback; данные сохраняются в именованном volume. Команда проверяет локальную цель и не предназначена для production или чужой базы.

`db:migrate` проверяет локальную цель и применяет версионированные SQL-миграции с checksum и блокировкой конкурентного запуска. `db:runtime` создаёт отдельную ограниченную runtime-роль и сохраняет административное соединение отдельно в приватной конфигурации. `db:check` выполняет только чтение: проверяет соединение и совпадение ожидаемой базы/роли, не показывая приватные параметры.

`owner:setup` создаёт единственного владельца: пароль 12–128 символов вводится скрыто дважды. Команда не перезаписывает существующего владельца. Не передавайте пароль в командной строке, через echo или чат. При необходимости восстановить доступ с подтверждённым серверным доступом: `npm run owner:reset`, также со скрытым вводом и отзывом всех сессий.

Если PostgreSQL уже работает вне Docker, настройте отдельную базу и миграционный доступ по [инструкции](docs/COOLIFY.md). `db:up`, `db:runtime` и `db:check` предназначены только для сгенерированной локальной тестовой базы. Не подменяйте подключение автоматически и не запускайте интеграционные тесты на рабочей базе.

Остановка приложения: `Ctrl+C`. Остановка тестовой БД с сохранением данных:

```powershell
npm run db:stop
```

Не удаляйте volume для обычного перезапуска.

## Конфигурация и безопасность

`.env.example` описывает переменные без рабочих секретов. `.env`, `.local/`, резервные копии и runtime-файлы исключены из Git и Docker build context. Переменные не должны иметь префикс `VITE_`, если они содержат приватные значения: такие переменные доступны браузеру.

Backend не логирует тела запросов, cookie, авторизацию, строки соединения и сырые ошибки PostgreSQL. Вместо них используются безопасные коды. TLS для БД задаётся отдельно: `DATABASE_TLS=verify-full` проверяет сертификат, `disabled` подходит для явно выбранной внутренней сети или локальной тестовой БД. SSL-параметры внутри строки соединения не допускаются, чтобы они не переопределяли проверку сертификата.

`/health/live` проверяет работу процесса. `/health/ready` возвращает 503, если БД не подключена. `/api/system/status` работает только вне production и не возвращает параметры доступа.

Production-сборка отдаётся самим backend из `dist/client`; серверная сборка находится в `dist/server`. Публичные assets ограничены списком собранных файлов, произвольные пути файловой системы не обслуживаются. В production включены CSP и защищённые cookie; допустимый origin берётся из HTTPS APP_URL.

## Работа с платформой

Первый вход открывает пустое хозяйство. Добавьте склады, клиентов и аренды; индивидуальная цена указывается при создании каждой аренды. Во вкладке оплат выберите аренду, месяцы и фактически полученную сумму, проверьте серверное распределение и зарегистрируйте поступление. Можно погасить часть суммы или несколько месяцев вперёд. Неоплаченные остатки видны в графике и обзоре.

В локальном режиме разработки в настройках доступно подтверждённое действие «Загрузить пример». Оно работает только на пустой бизнес-базе и никогда не доступно в production. Для реальной работы начинать с чистой базы без примера; автоматического удаления демоданных нет.

Аренда бессрочная до ручного действия «Освободить склад». Склад сразу доступен для новой аренды; начавшийся месяц, долг и оплаты сохраняются без перерасчёта, начисления следующих месяцев отменяются. Подробнее: [BUSINESS_RULES.md](docs/BUSINESS_RULES.md). Перерасчёт по дням, депозиты и реальные возвраты не входят в текущую версию.

## Telegram и Coolify

Токен задаётся только в серверном окружении. В админке укажите получателя, число дней (по умолчанию 5) и время, затем явно включите уведомления. Тестовая отправка — отдельное подтверждённое действие. Без Telegram учёт оплат продолжает работать.

Планировщик backend запускается раз в минуту и не зависит от открытой страницы. Очередь сохраняется в PostgreSQL. Неопределённая доставка не повторяется автоматически, чтобы не послать дубликат.

Готовы production Dockerfile, healthcheck и [подробная инструкция Coolify](docs/COOLIFY.md), включая ограниченную роль, release-миграции, резервные копии и восстановление доступа. Пользователь переносит проект в Git и разворачивает отдельно; реального deployment из этой рабочей папки не выполнялось.

Приватный `.env.production` подготовлен для заполнения внешнего подключения; в Git идёт только `.env.production.example`. На первом запуске с `INITIALIZE_EMPTY_DATABASE=true` схема создаётся автоматически после проверки пустоты и ожидаемой идентичности. После первого успешного запуска и настройки владельца выключить этот флаг. На последующих обновлениях с новой схемой нужны проверенный backup и отдельная команда миграций.

## Проверки

Интеграционные и browser-проверки создают отдельные временные базы с проверенным префиксом на локальной PostgreSQL, затем удаляют только их. Основная локальная база сохраняется. Для браузерного сценария используется установленный Chrome; трассы, cookie, пароли и сырые запросы не сохраняются. Визуальные снимки тестовых данных остаются только в игнорируемой `.local/screenshots/`.

Тесты Telegram используют синтетический провайдер и не отправляют настоящие сообщения. Production-готовность к конкретному домену и боту проверяется уже при подключении владельцем.
